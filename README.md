# proof

Заявление с доказательством, которое можно перепроверить.

Проблема настоящая: в переписке агентов и людей «работает» означает «я запустил и вот
вывод». Через день это утверждение нельзя проверить — вывод остался в чате, команда
забыта, репозиторий уехал. Здесь заявление хранится вместе с **точной командой** и
**отпечатком вывода**, и любой следующий участник перепроверяет его одной командой.

```bash
proof add --claim "80 тестов зелёные" --cmd "python3 -m unittest discover -s tests -t ." --dir repo
proof check
proof list
proof show --id 1
```

## Три вердикта

| Вердикт | Что значит |
|---|---|
| `подтверждено` | команда вернула ожидаемый код, вывод тот же |
| `устарело` | работает, но вывод изменился: заявление надо переписать, а не паниковать |
| `сломано` | код не тот: доказательство перестало быть доказательством |

Отпечаток считается по **нормализованному** выводу: числа-тайминги (`0.012s`) заменяются
на `<t>`, иначе каждый прогон тестов давал бы `устарело` из-за миллисекунд. Поэтому
`Ran 80 tests in 0.01s` и `Ran 80 tests in 1.4s` — один отпечаток, а `Ran 82 tests` — другой.

## Проверка

```bash
$ cargo test
test result: ok. 8 passed; 0 failed

$ cargo run -q -- demo
итог: 6 проверок, 0 провалов
```

## Живой прогон на настоящем реестре

Реестр четырёх наших репозиториев (`proofs/`), плюс одно заведомо устаревшее заявление
из старого `HANDOFF.md` («hubd: ровно 20 тестов»):

```
$ proof check
#1   подтверждено   hubd: тесты зелёные
#2   подтверждено   tupleboard: все тесты ok
#3   подтверждено   homeostat: все тесты ok
#4   подтверждено   stigmergy: все тесты ok
#5   подтверждено   proof: все тесты ok
#6   сломано        hubd: ровно 20 тестов, как в HANDOFF

итог: подтверждено 5, устарело 0, сломано 1
(код проверки: 1)
```

Шестое — ровно то расхождение, из-за которого уже переделывали README: в `hubd` сейчас
80 тестов, а не 20.

## Правила

1. Заявление — это **фраза**, которую кто-то произнёс, и **команда**, которой её проверяют.
2. `add` сразу запускает команду: заявление не сохраняется непроверенным.
3. Ожидаемый код задаётся (`--expect 1`), поэтому «проверка должна падать» — это тоже
   законное доказательство.
4. `check` перепроверяет всё и возвращает 1, если хоть одно заявление сломано, — годится
   для CI и для крона.
5. Реестр — каталог `proofs/` с плоскими текстовыми файлами: можно держать в git.

## Чего это не делает

- не заменяет тесты: оно фиксирует, что тесты запускаются и дают тот же результат;
- не ловит изменение, если вывод изменился «в пределах нормализации» (тайминги);
- не запускает команды по расписанию само — для этого `check` зовут из крона/CI;
- не хранит полный вывод, только хвост (три строки) и отпечаток;
- команда без таймаута: зависшая команда подвесит проверку.

## Провенанс

Идея «доказательство, а не слово» — из практики нашей команды: `HANDOFF.md` утверждал
20 тестов, реальность — 80; README обещал 47/47 обходов, независимая проверка дала
45/47. Формат — часть [Череды](https://github.com/kostyk348/chereda), где доказательство
требуется при каждом объявлении «сделано».
